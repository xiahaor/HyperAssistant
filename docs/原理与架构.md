# 原理与架构

> 本文讲"这东西是怎么工作的"。
> 接口签名、结构数据、踩坑与未解问题在 **[逆向数据与经验.md](逆向数据与经验.md)**（那份是活文档，标注了证据强度）。

---

## 1. 一句话

**不自己画动画**，而是 hook 系统自己的 **HyperViewScale（HVS）过渡引擎**，
让负一屏的「卡片 → 应用」走系统原生过渡，并把这个过程变成**可控、可关、可调试**的。

为什么不自绘：负一屏的内容由 **MAML(Rust)** 绘制、窗口 SurfaceControl 归 **WMS** 管，
外部无法安全地变换它的内容或窗口 —— 自绘/贴图那条路在本项目的历史里已被多次证伪
（详见逆向文档的"踩坑速查表"与判废清单）。

```
┌───────────────────────────────────────────────────────────────────────┐

│   · AssistantOverlayWindow / AssistContentView（内容与滑入滑出）        │
│   · ★ 模块 hook 点：HVS 远程过渡的请求与回调、mask / leash / crop 写入   │
└───────────────────────────────────────────────────────────────────────┘
                              ▲ 权限与白名单判定
┌─────────────────────────────┴─────────────────────────────────────────┐
│ system_server （模块也注入这里，只为"放行"）                            │
│   · ActivityTaskManagerService.checkPermission                          │
│   · HyperViewScaleConfigManager.isHyperViewScaleAllowedUid 等           │
└───────────────────────────────────────────────────────────────────────┘

┌──────────────────────────┐        广播 SETCFG（k/v）        ┌──────────┐
│ App com.qianxia.Hyper…   │ ────────────────────────────────▶│ 宿主进程  │
│ （Compose UI，4 个页面）  │ ◀──── 日志推送 / PONG 心跳 ───────│ 接收器    │
└──────────────────────────┘                                  └──────────┘
```

**为什么要碰 system_server**：非系统 uid 在 `startActivity` 时若带 `remoteTransition`，
会被 `CONTROL_REMOTE_APP_TRANSITION_ANIMATIONS` 权限卡住（日志里表现为
`Permission Denial: … with remoteTransition`）。负一屏不是系统 uid，
所以必须由 system_server 侧放行，HVS 过渡才可能被接受。

## 3. 代码结构与"31 个文件零改动"

```
app/src/main/
├── java/com/qianxia/hyperassistant/          ← hook 侧（宿主/system_server 里跑）
│   ├── Entry.java            API 102 入口：把生命周期回调转给 MainHook
│   ├── MainHook.java         按包名分发到各安装点（主线逻辑的总入口）
│   ├── AssistantAnimCore.java  主线核心（过渡接管、mask/crop/leash 处理、日志）
│   ├── SystemServerHooks.java  只在 system_server 生效的"放行"钩子
│   ├── Bridge.java / LogPush.java / Diag.java   与 App 的桥：PING/PONG、日志推送、落盘
│   ├── RtCfg.java            运行期配置：App 推来的键值 → 写进字段 + 落盘
│   ├── CoreConfig.java / Config.java  开关（**非 final**，才能运行期改）
│   └── de/robv/android/xposed/…         API 82 兼容垫片（见下）
└── kotlin/com/qianxia/hyperassistant/        ← App 侧（Compose UI）
    ├── MainActivity.kt / ModuleSettings.kt（4 个页面）/ LogStore.kt
    ├── Theme.kt / PageTransition.kt / liquid/…
    └── effect/               关于页「流光溢彩」背景（AGSL 运行期着色器）
```

### 3.1 为什么要写一层"API 82 兼容垫片"

主线那套逻辑是用 **Xposed API 82** 写的（`XposedBridge` / `XposedHelpers` / `XC_MethodHook`，
共 92 + 19 + 34 处调用）。迁到 **libxposed API 102** 时，如果逐处改写，风险与工作量都很大。

于是本项目在**自己的 APK 里**实现了一套 `de.robv.android.xposed.*`，架在 API 102 之上：

```
XC_MethodHook.before/after  →  Chain（proceed / 返回值 / 异常）
XposedHelpers.callMethod…   →  纯反射实现
XposedBridge.hookAllMethods →  XposedInterface.hook(m).intercept(...)
```

⇒ 业务文件**一行未改**，只需要在 `Entry` 里把 API 102 的生命周期
（`onModuleLoaded` / `onSystemServerStarting` / `onPackageLoaded` / `onPackageReady`）
转成 API 82 那套 `LoadPackageParam` 即可。

> 细节（含各参数类型真正有哪些方法）见逆向文档 §1；那里也记了"`PackageLoadedParam`
> 没有 `getClassLoader()`"这类只有踩过才知道的点。

## 4. 运行期配置（为什么必须去掉 `final`）

**坑**：`public static final boolean X = true;` 是**编译期常量**，会被**内联进每个调用点**
⇒ App 或广播在运行期改它**毫无效果**（连反射都改不动，因为读的是字面量）。

**做法**：

1. 把要接管的开关改成 `public static`（非 final），默认值保持不变（不配置时行为不变）；
2. App 侧发广播 `com.qianxia.HyperAssistant.SETCFG`（`k` / `v`）；
3. 宿主进程的接收器（复用已有的 `Bridge` 接收器）收到后**直接写字段** + **落盘**
   `/sdcard/Download/dsh-debuglog/animv4.conf`；
4. 同时打一行**当前配置快照**日志 ⇒ 只看日志就能判断"生效没生效"。

⇒ 效果：App 上拨一下开关，**下一次动画就按新值走**，不用重装、不用重启。

## 5. UI 侧三个设计决定

1. **关于页的流光背景画在根布局，不画在页面里。**
   实测：把 AGSL 着色器画在 `HorizontalPager` 的某一页里**完全看不见**
   （纯色矩形能看见 ⇒ 极易误判成"没生效"）——页的绘制坐标系带横向平移。
   现在画在根布局，用"离关于页的距离 × (1−滚动进度)"做 alpha，顺带把逐帧重绘限制在可见时。

2. **搜索/滚动类"让位"只留一份。**
   底栏是悬浮胶囊，内容既给了 `contentPadding.bottom` 又在尾部加了 `Spacer`
   ⇒ 空隙翻倍（用户一眼看出"底部空缺太大"）。

3. **淡出 ≠ 让位。**
   给某块内容做 alpha 淡出时，它的**高度仍然占着**。要"淡出且不留白"，
   必须把那块改成**浮层 + 列表里的 spacer**（内容从它下面滚过）——本项目目前选择了不做淡出。

## 6. 一次打开动画里，模块都做了什么（简版）

1. 负一屏里点击卡片 → 请求带 `remoteTransition` 启动应用
2. system_server 侧钩子**放行**该请求（否则被权限拒绝，动画根本不会发生）
3. HVS 引擎开始过渡；模块在负一屏进程里介入：
   - 记录/修正 **leash 的几何写入**（让应用窗口按需要的尺寸与位置出现）
   - 处理 **mask 面**（`view_scale_mask`）：这是"色块 / 露内容"两个症状的来源
   - 处理 **crop** 与必要时的模糊
4. 过渡结束做收尾（释放/隐藏我们动过的面），把状态放回 `AT_REST`

> 每一步的开关都在 App 的「设置」页里可查可关；出问题时**先关掉最近的开关**再定位。

## 7. 已知问题与取舍

- **闪黑**：历史遗留，唯一候选解释证据不足（见逆向文档 §9）
- **下拉回弹**：用 Compose 自带的拉伸；MIUIx 的阻尼节点在本项目层级实测不生效
- **mask 的两难**：把铺色收窄 ⇒ 露应用实时内容；铺满 ⇒ 整屏变成组件主色
  （桌面靠"同时驱动两层"绕开，本项目尚未做成）

## 8. 想改代码的话，从哪看起

| 想改什么 | 看哪 |
|---|---|
| 开关的默认值 / 新增一个开关 | `CoreConfig.java`、`Config.java` → 再加进 `RtCfg.KEYS` 与 App 的开关表 |
| 与 App 的通信（心跳、日志、配置） | `Bridge.java`、`LogPush.java`、`Diag.java` |
| 过渡接管的核心行为 | `AssistantAnimCore.java`（很大，按日志里的中文关键词搜） |
| system_server 放行 | `SystemServerHooks.java` |
| UI 四个页面 | `ModuleSettings.kt` |
| 流光背景 | `effect/`（Apache-2.0，见 `NOTICE`） |
